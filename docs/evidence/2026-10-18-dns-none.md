# No-resolver modes of the bridge: `--dns none` and `--ipv6-dns none` (2026-10-18)

The bridge documents two ways to say "announce no resolver": `--dns none` for
IPv4 and `--ipv6-dns none` for the second, IPv6-only passt. `umnet` settles
each nameserver itself before forking (passt must never be left to read a host
`resolv.conf` that Android does not have) and passes `-D none` to that
helper. This record closes the review item that the IPv6 half of that
behaviour had been added but never exercised on the device.

Verifying it found a **gate defect, not a bridge defect**:
`test-umnet-network.sh` used `--ipv6-dns none` as its own "skip IPv6 egress
checks" switch and **never forwarded the value to `umnet`**. The IPv6 helper
therefore fell back to the host/public resolver while the gate believed the
option was off -- and the gate skipped exactly the checks that would have
noticed. Fixed in `harness: forward --ipv6-dns none and gate the no-resolver
modes` (PR #19), together with a `--dns none` gate mode and a per-helper
check (below).

Device: Termux host (Xiaomi 23124RN87C, Android 15 / SDK 35, host kernel
5.15.194); release assets `linux-bionic` `b778f4f7…`, `stub_exe`
`731c48d5…`, `umnet` `7683b4f8…`, `passt-bionic` `502d980c…`.

## How the gate observes "no resolver"

Both helpers share one pty, so their start-up configuration is interleaved in
the guest log. Each passt prints one `DNS:` block **iff** it announces
resolvers, so the gate counts occurrences (not lines: one line can hold
`DNS:DNS:` when the two helpers write at the same time) and requires exactly
one per helper configured to announce one. That is per-helper evidence that the
options reached the processes, not just the guest-visible half.

For `--dns none` the gate also clears a stale guest `/etc/resolv.conf` from a
previous round, drops the checks that need a resolver (resolver config, lookup,
TCP by name, six-way concurrency) and asserts instead that the guest ends up
with no IPv4 nameserver.

## Runs

| record | options | checks | resolver blocks | result |
| --- | --- | --- | --- | --- |
| `2026-10-18-umnet-network-dns-none.json` | `--dns none --ipv6 --ipv6-dns none` | 10/10 | **0** | PASS, 134.2 s |
| `2026-10-18-umnet-network-ipv6-dns-none.json` | `--ipv6 --ipv6-dns none` (IPv4 resolver on) | 13/13 | **1** (IPv4 only) | PASS, 41.6 s |

The first run is the one that matters: both helpers were told `-D none`, and
the guest still got DHCP (10.0.2.15/24), a default route, loopback/ICMP, an
IPv6 address on `vec0` (fd00::2), the IPv6 default route via fe80::1 and a
successful `ping6` to the gateway -- no resolver needed, none announced. Its
longer duration is the guest's own DNS/TCP retry loops running without a
resolver; the judged checks do not depend on them.

The second run is the control for the per-helper count: only IPv6 has its
resolver disabled, so exactly one `DNS:` block (the IPv4 helper's) appears and
all IPv4 name-resolution checks still pass. It also confirms the two options
are independent -- `--ipv6-dns none` does not disable the IPv4 resolver, and
vice versa.

Verification: `record-evidence.sh check --verify-hashes` passes for both
records on the device (component hashes above), and the same offline `check`
passes in the container.

## Not verified

- The wire contents (RA RDNSS option, DHCPv6 DNS option) were not captured with
  a packet sniffer; the evidence is the helper configuration the processes
  print plus what the guest ends up with. A guest that ignores RA/DHCPv6
  resolver options could not make the wire-level claim either way here.
- IPv6 DNS egress is not exercised in these runs, by design: the gate skips
  egress checks when the resolver is disabled.
- One device and one network only; the unrelated note that this phone's UDP
  path drops plain DNS queries occasionally still applies to the runs that do
  use a resolver.
